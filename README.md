# Room Booking System

Мини-система бронирования переговорных комнат.
REST API на Spring Boot + SPA на Vue 3.

## Стек технологий

**Backend:**
- Java 26+ / Spring Boot 4
- Spring Web (REST), Spring Data JPA
- PostgreSQL 18 (Docker)
- Lombok, Bean Validation, Swagger UI

**Frontend:**
- Vue 3 + Vite
- Vue Router 4, Pinia, Axios

## Требования

- Docker Desktop
- JDK 26+
- Node.js 20+

## Игры

В карточке **Games** на главной доступны две игры.

**Minesweeper** — поле 9×9, 10 мин. Очки за победу считаются на сервере:
клиент присылает только время и число верных флажков, а бэкенд по ним
выводит баллы (`POST /api/games/minesweeper`).

**Solitaire** — клондойк: колода и четыре основания сверху, семь рядов
внизу. Карты таскаются мышью на ряд или основание; место сброса
подсвечивается зелёным, если ход законный, и красным, если нет.
Клик по карте тоже работает — на случай тач-экрана. Отмена хода — по
`Ctrl+Z` (`Cmd+Z` на macOS), новая партия — кнопкой с пикой в панели,
под кнопкой меню. Нижних кнопок под столом нет. Двойным кликом карта
уходит в основание.

Правила и раздача лежат в `frontend/src/games/solitaire.js` и не зависят
от Vue, поэтому тестируются отдельно: там же проверка допустимости хода
(`canDropOnTableau`, `canDropOnFoundation`), по которой рисуется
подсветка при перетаскивании — она обязана совпадать с настоящим
результатом хода, иначе подсветка будет врать.

Под столом показывается и состояние партии: «Ходов больше нет — партия
зашла в тупик» (`hasAnyMove`) и «Ходов по столу нет — осталось только
перебирать колоду» (`hasBoardMove`). Второе состояние — обычное дело,
оно встречается примерно в 5% позиций: колоду можно крутить сколько
угодно, но ни одна карта никуда не ложится. А вот настоящего тупика в
клондойке с безграничным перебором колоды не бывает: если карты
перестали помещаться на стол, минимальная из них всегда ложится либо в
основание, либо в ряд, и так до полной победы. Проверка `hasAnyMove`
оставлена как защита на будущее, если правила или колода изменятся.

Автодобор: как только закрытых карт не осталось и колода с отбоем
пусты (`allCardsRevealed`), дальше идти незачем — панель строит план
(`planAutoFinish`) и сама убирает оставшиеся карты в основания каскадом
с анимацией. План ищется сначала переносами в основания, а если они
кончились — перекладыванием стопок между рядами; если дойти до победы
не выходит, план возвращает `null` и партия доигрывается вручную. Пока
идёт автодобор, поле не принимает клики и таймер стоит: партию игрок
доиграл сам, до последнего хода. Сделанные автоматически ходы в счёт
«аккуратности» не идут — в очки уходят только ходы игрока.

Очки, как и в сапёре, считает сервер (`POST /api/games/solitaire`):
за победу 300, за скорость до 300 и за аккуратность до 200.

Накопленные очки по каждой игре видны в профиле.

Раскрытая карточка занимает разное место: сапёр — две колонки сетки
и два ряда, пасьянс — две колонки и три ряда (семи колонок с
разъезжающимися картами в высоту двух карточек не помещается, а в одну
колонку сетки настоящие карты тесноваты). На совсем узком экране
пасьянс остаётся в одной колонке, а карты уменьшаются. Место под самый длинный ряд зарезервировано заранее,
чтобы карточка не менялась в размере посреди партии.

### Сокеты

`/ws/rooms` — односторонний: сервер рассылает события (список комнат,
изменения расписания) всем подключённым, входящих сообщений не ждёт и
личность игрока не знает — соединение публичное.

Если понадобится игра на двоих, этому сокету не хватает трёх вещей:
обработки входящих сообщений, адресной отправки конкретному игроку и
опознания пользователя (токен придётся передавать в query-параметре:
браузер при апгрейде на WebSocket не умеет слать заголовки).

## Запуск

Нужно **3 терминала**.

### 1. База данных

Из **корня** проекта:
```bash
docker compose up -d postgres
```

### 2. Бэкэнд

Из папки **backend/**:
```bash
./mvnw spring-boot:run
```

### 3. Фронтенд

Из папки **frontend/**:
```bash
npm install   # только в первый раз
npm run dev
```

Открыть: http://localhost:5173
## Консольные команды

Интерактивная оболочка Spring Shell. Живёт под профилем `cli`: без него
оболочка не поднимается, поэтому обычный запуск и контейнеры не задеты.
Веб при этом не поднимается — командам он не нужен.

Из папки **backend/**:
```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments="--spring.profiles.active=cli"
```

| Команда | Что делает |
|---|---|
| `promote --username <логин>` | Выдаёт роль `ADMIN`. Через API это невозможно: регистрация всегда создаёт `USER`, поэтому без этой команды админку не открыть. |
| `report` | Ищет аномалии: брони с прошедшим временем в статусе `ACTIVE`, активные брони в отключённых комнатах, комнаты с одинаковым именем, пользователи без броней и игр. |
| `export --from 2026-01-01 --to 2026-12-31 --out exports` | Выгружает `bookings.csv`, `users.csv`, `game-stats.csv`. Период по умолчанию — всё. |
| `backup --out backups` | Снимок базы в JSON. Пишется на Java, без `pg_dump`: в образе `jre-alpine` его нет. Пароли в снимок не попадают. |

Однократный запуск без терминала — для CI и скриптов. Настройки уходят
через переменные окружения, чтобы в аргументах осталась только команда:
```bash
SPRING_PROFILES_ACTIVE=cli SPRING_SHELL_INTERACTIVE_ENABLED=false \
SPRING_MAIN_WEB_APPLICATION_TYPE=none \
java -jar target/booking-0.0.1-SNAPSHOT.jar report
```

## Админ-панель

http://localhost:5173/admin — сводка по системе и управление комнатами:
создание, правка, отключение. Отключённые комнаты остаются в списке
админки, но пропадают из публичного.

Права выдаёт команда `promote` из консоли (см. выше). Админка живёт на
`/api/admin/**` под `hasRole("ADMIN")`; создание, правка и отключение
комнат — на уже существующих `/api/rooms` с тем же правилом, поэтому
дублирующих эндпоинтов нет.

Роль приходит в `UserResponse`, а не только при логине: без этого после
F5 страница не знала бы, показывать ли админские ссылки.
